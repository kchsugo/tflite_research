# 다중 task CPU/GPU 배분 — 발표 자료 설명 파일

> 이 문서는 PPT 제작용 슬라이드 대본이다. 각 슬라이드마다 **[슬라이드에 넣을 내용]**과
> **[발표 노트]**를 함께 적었다. 흐름: 단일 task 성과 → 다중 task 문제 → 아이디어들과 그 한계
> → 그 한계 때문에 "통짜 라우팅" 선택 → 배분 알고리즘 → 예시.

## 슬라이드 1 — 제목

**[내용]**
- 제목: **TFLite 환경에서 다중 DNN task의 효율적 CPU/GPU 배분**
- 부제: 단일 task 내부 분할에서 다중 task 스케줄링으로
- 발표자 / 날짜

**[발표 노트]**
- 한 줄 정의: TFLite delegate는 "어디가 효율적인가"를 안 본다. 우리는 그 빈자리를 채운다.

---

## 슬라이드 2 — 문제의 출발점: delegate는 효율을 안 본다

**[내용]**
- TFLite GPU delegate의 파티셔닝 = **지원 여부 기반 + 탐욕적(greedy)**
- 지원되는 op는 최대한 큰 덩어리로 묶어 전부 GPU로 보냄
- **op별 "어디가 빠른가" 비용 모델이 없다** → GPU가 지원하지만 CPU가 더 빠른 op도 그냥 GPU로
- 정확한 요약: "지원되고 충분히 큰 덩어리면 GPU로. **효율은 기준이 아니다.**"

**[발표 노트]**
- 이 "효율을 안 본다"가 전체 연구의 문제의식. 단일 task든 다중 task든 여기서 출발.

---

## 슬라이드 3 — 기존 성과: 단일 task 내부 분할 (internal split)

**[내용]**
- 목표: 모델 하나를 단일 인터프리터에서 CPU/GPU로 **내부 분할**, 최적 절단점 오프라인 확정
- 방법: GPU delegate의 `first_delegate_node_index = k` 레버로 "노드 0..k-1은 CPU, k.. 는 GPU"
- 절단점 k를 훑으며(sweep) **절단점별 전체 latency 실측** → 가장 빠른 k 선택
- 비용 모델: `비용(k) = Σ GPU compute + (경계 텐서 ÷ PCIe 대역폭) + Σ CPU compute`
- **결과물: "단일 task, GPU 한가함" 조건의 최적 절단점 = preset 1개**

**[발표 노트]**
- 여기까지가 이미 구현/검증된 부분. 단 이 preset은 **부하 0일 때만 최적**이다(다음 슬라이드).

---

## 슬라이드 4 — 새 문제: 다중 task와 GPU pile-up

**[내용]**
- 현실: 추론 요청은 **여러 task가 동시에** 들어온다
- GPU vs CPU 비대칭:
  - **GPU = 직렬 단일 자원** (사실상 한 번에 하나, 비싼 컨텍스트 스위치)
  - **CPU = 병렬 자원** (코어 수만큼 진짜 동시)
- N개 task가 각자 GPU로 무거운 conv를 보내면 → **GPU에서 직렬화 + 대기(pile-up)**, 그동안 CPU 코어는 논다
- 큐잉 이론: GPU 이용률 ρ→1에서 대기시간 발산. "개별 최적(각자 GPU)"이 모여 "전체 최악"

**[발표 노트]**
- 문제 성격이 바뀐다: **partitioning(어디서 자르나) → scheduling(누구를 어디로 보내나).**

---

## 슬라이드 5 — 핵심 통찰: 입도는 부하에 따라 뒤집힌다

**[내용]**
- **task 1개 + GPU 한가** → 모델을 잘게 쪼개 CPU/GPU 둘 다 써서 그 하나의 지연을 줄이는 게 이득
- **task 여러 개 몰림** → 쪼개면 **손해**
  - 병렬성은 이미 task 개수에서 나옴
  - 쪼개면 task마다 경계 전송(PCIe)만 추가됨
- 결론: **부하가 높으면 쪼개지 말고 task 통째로 배정하라**

**[발표 노트]**
- 이 통찰이 다음 아이디어들의 채점 기준이 된다. "쪼개는 아이디어"는 다중 task에서 왜 지는가.

---

## 슬라이드 6 — 아이디어 ①: op 단위 분할 (GPU-빠른 op만 골라 GPU로)

**[내용]**
- 발상: 각 task에서 **GPU가 CPU보다 훨씬 빠른 op**을 우선순위 큐에 넣어 GPU로, 나머지는 CPU로
- 신호는 옳다: **op별 speedup 비율(C/G)** = delegate가 못 보는 바로 그 효율
- **한계 3가지:**
  1. **의존 사슬** — 한 task 내부 op은 일렬 의존. op5는 op4 출력이 있어야 시작 → GPU-part와 CPU-part를 **동시에 못 돌림**
  2. **파편화 세금** — 흩어진 op을 고르면 경계마다 PCIe 왕복 + PHWC4 레이아웃 변환. discrete GPU에선 speedup을 까먹음
  3. **측정 난이도** — op별 GPU 시간은 delegate가 op을 하나의 커널로 흡수해 재기 어려움

**[발표 노트]**
- 이 아이디어는 "다중 task이고 op이 흩어졌을 때"만 유효한데, 그때 파편화 비용이 이득을 먹는다.

---

## 슬라이드 7 — 아이디어 ②: task별 1 절단점 (각 task를 한 번 쪼개 동시 실행)

**[내용]**
- 발상: 각 task를 internal split처럼 한 번 쪼개(CPU-part + GPU-part), 여러 개를 동시에 실행
- **한계:**
  - N개 task의 **GPU-part가 전부 공유 GPU로 몰림** → pile-up 그대로 재발
  - 게다가 task마다 **경계 전송(PCIe)까지 추가**
  - → GPU 혼잡 + 경계 비용을 **둘 다** 떠안는, 다중 task에선 대체로 최악

**[발표 노트]**
- CLAUDE.md 원칙 "부하 높으면 쪼개지 말라"의 반례 실증. 쪼갤수록 GPU에 더 몰린다.

---

## 슬라이드 8 — 아이디어 ③: 오프라인 정적 배분 (미리 확정)

**[내용]**
- 발상: 어느 task를 어느 device에 보낼지 **오프라인에 미리 확정**
- **분리해서 봐야 함:**
  - **오프라인 측정(C, G, 경계 크기)** → 항상 함 ✅
  - **오프라인 정적 배정** → **도착이 예측 가능할 때만 유효**
- **한계:** 도착이 동적/버스트면 정적 배정이 pile-up을 못 막음
  - "task타입 X는 항상 GPU"로 굳혀도 X가 10개 동시에 오면 GPU에 그대로 쌓임
  - pile-up의 원인은 task 정체성이 아니라 **도착 타이밍**
- → 원칙: **비용표는 오프라인, 배정 결정은 온라인(부하 인지)**

**[발표 노트]**
- 이게 다음 슬라이드 LaLaRAND가 "왜 오프라인으로 되는가"의 열쇠 — 걔넨 주기적 실시간이라 도착을 안다.

---

## 슬라이드 9 — 관련연구 LaLaRAND: 왜 그대로 못 쓰나

**[내용]**
- LaLaRAND (RTSS 2021): layer 단위 CPU/GPU 스케줄링. **잘게 쪼개서 실행**
- "그럼 걔네도 같은 pile-up 있지 않나?" → **경합은 있다. 근데 3가지 완충장치로 관리한다:**

| LaLaRAND의 전제 | 우리 (RTX 5060 + TFLite) |
|---|---|
| **통합 메모리**(Jetson) → 경계 전송 거의 공짜 | **discrete GPU** → 경계마다 PCIe + PHWC4, 비쌈 |
| **주기적 실시간** → 도착 알아서 오프라인 회피 | **동적/동시 도착** → 오프라인만으론 못 막음 |
| **CPU 양자화**로 CPU를 도피처로 | fp32면 CPU가 느려 도피처 약함 |

- 결론: LaLaRAND는 **통합메모리·실시간** 세계의 해법. 우리 환경엔 그 완충장치가 없어 **그대로 복붙하면 경계 비용에서 무너짐**

**[발표 노트]**
- 핵심 한 문장: "걔넨 파편화가 싸서 잘게 쪼갤 수 있고, 우린 비싸서 못 쪼갠다."

## 슬라이드 10 — 결정: 각 task를 통짜로 CPU/GPU에 라우팅

**[내용]**
- 위 아이디어들의 한계(쪼개면 경계 비용·pile-up 재발)를 근거로 **선택:**
- **각 task를 쪼개지 않고 통째로 CPU 또는 GPU 한쪽에 배정**
  - 경계 전송 **0** (discrete GPU의 PCIe 비용 회피)
  - 병렬성은 task 개수에서 확보
  - 노는 CPU 코어를 **처리량 방어선**으로 활용 → GPU pile-up을 "안 만들기"로 해결
- 남는 질문: **그럼 어떤 task를 GPU에, 어떤 task를 CPU에?** → 배분 알고리즘

**[발표 노트]**
- "단일(개별) task 통짜 배정"이 우리의 선택. 다음 두 슬라이드가 이 발표의 핵심 기여.

## 슬라이드 11 — 문제 형식화

**[내용]**
- 가정: **서로 다른 모델 N개**가 **동시에** 도착 (discrete GPU)
- 각 task i의 측정값:
  - `G_i` = 전부 GPU로 돌릴 때 시간
  - `C_i` = 전부 CPU로 돌릴 때 시간
- 자원 모델:
  - GPU 직렬: `GPU_finish = Σ_{i∈GPU} G_i`
  - CPU 병렬: `CPU_finish = CPU_makespan(CPU set)`
- 목표(동시 도착이니 **makespan** = 전부 끝나는 시간):
  - `min max( GPU_finish , CPU_finish )`
- 직관: **두 device가 거의 동시에 끝날 때(균형점)** makespan 최소

**[발표 노트]**
- 균형은 "목표를 같게 만들자"가 아니라 "늦은 쪽을 최소화"한 **결과**. task가 원자적이라 정확히 같아지진 않음.

---

## 슬라이드 12 — 배분 알고리즘: 비율 우선 + 균형 그리디

**[내용]**
- 두 직관을 한 알고리즘에 결합:
  - **GPU는 희소 직렬 자원 → speedup 큰(`C_i/G_i` 큰) task부터 GPU로** (GPU 1초당 CPU 시간 최대로 아낌)
  - **GPU_finish가 CPU_finish를 넘기 직전에 멈춤** (균형 = makespan 최소)

```
1. 처음: 모든 task를 CPU에      (GPU_finish = 0, CPU_finish = ΣC_i)
2. C_i / G_i 내림차순 정렬        (GPU에서 가장 이득 큰 것부터)
3. 앞에서부터 task를 GPU로 이동:
       GPU_finish += G_i
       CPU_finish -= C_i
   max(GPU_finish, CPU_finish)가 줄어드는 동안 계속
4. GPU_finish > CPU_finish 되는 순간(교차점) 정지 → 균형점
```

- **GPU_finish의 역할 = "그만 옮겨라" 브레이크.** 없으면 전부 GPU로 몰려 pile-up 재발
- 오프라인 + N 작음 → 최적을 원하면 `2^N` 전수/DP로 정확히도 가능

**[발표 노트]**
- 강조: 거의 모든 task가 GPU에서 빠르므로(C/G>1), 브레이크 없이 "이득 큰 것 옮기기"만 하면 전부 옮겨진다. GPU_finish가 혼잡 비용을 반영하는 변수.

## 슬라이드 13 — 예시 (숫자로 확인)

**[내용]**
- task 4개 (CPU 직렬 가정):

| task | C_i | G_i | 비율 C/G |
|---|---|---|---|
| A | 100 | 10 | 10 |
| B | 80 | 10 | 8 |
| C | 60 | 30 | 2 |
| D | 40 | 30 | 1.3 |

- 비율 내림차순(A→B→C→D)으로 옮기며 추적:

| 단계 | GPU_finish | CPU_finish | makespan |
|---|---|---|---|
| 시작(전부 CPU) | 0 | 280 | 280 |
| A 이동 | 10 | 180 | 180 |
| B 이동 | 20 | 100 | 100 |
| **C 이동** | **50** | **40** | **50 ← 최소** |
| D 이동 | 80 | 0 | 80 (악화) |

- C를 옮긴 순간 GPU(50) > CPU(40) = 교차 → **정지**. 최적 makespan = 50
- 브레이크 없이 D까지 옮기면 80, 전부 옮기면 pile-up

**[발표 노트]**
- "전부 GPU(delegate 기본)"였다면 makespan = ΣG = 80이고 CPU는 내내 논다. 우리 배분은 50 — CPU를 방어선으로 써서 이긴다.

## 슬라이드 14 — 실시간 측정 설계

**[내용]**
- `C_i`, `G_i`는 고정 상수가 아니라 **런타임 상태에 따라 변함**(캐시, 온도, 다른 부하)
- 설계: **오프라인 프로파일을 baseline으로, 실행 중 실측값으로 갱신**
  - 매 Invoke의 실제 소요시간을 이동평균으로 반영 → 배분기 입력 갱신
- 확정 필요한 측정 항목:
  1. **CPU 병렬 모델** — task당 1코어 동시(a) vs task당 전 코어 직렬(b), 어느 쪽이 빠른지 → 비용함수 확정
  2. 여러 모델의 `C_i`, `G_i` (internal split의 k=0=G, k=N=C 재사용)
  3. 실제 pile-up 재현 — 여러 인터프리터가 GPU를 동시에 때릴 때 직렬화되는지 실측

**[발표 노트]**
- "정적 분할점 + 동적 배정" 원칙 유지: 무거운 계산은 오프라인, 런타임은 실측 갱신 + 선택만.

## 슬라이드 15 — 정리 & 향후 과제

**[내용]**
- **기여:**
  1. delegate가 못 보는 **효율(C/G)** 을 배분 신호로 사용
  2. 다중 task에서 쪼개기의 한계(경계 비용·pile-up) 규명 → **통짜 라우팅** 선택
  3. **비율 우선 + 균형(GPU_finish 브레이크)** 그리디 배분 알고리즘 + makespan 최적화
- **연구 흐름:** 단일 task 내부 분할(완료) → 다중 task 통짜 배분(본 발표) → 실시간 측정 통합
- **향후:**
  - CPU 병렬 모델 확정 후 실모델로 그리디 검증
  - pile-up 실측 → A/B(엣지 프록시 vs desktop 타깃) 확정
  - 부하 낮을 때 internal split preset 재활용(부하 적응형)

**[발표 노트]**
- 마무리 메시지: 부하가 낮으면 쪼개고(단일 task 최적화), 높으면 통짜 배분한다. "쪼개는 횟수를 부하에 반비례시킨다."

## (부록) 발표 한 장 요약 — 아이디어 → 한계 → 선택

| 아이디어 | 핵심 | 한계 | 판정 |
|---|---|---|---|
| ① op 단위 분할 | GPU-빠른 op 우선 | 의존 사슬 + 파편화 + 측정난이 | 다중 task에서 부적합 |
| ② task별 1 절단 | 각 task 1회 분할 동시실행 | GPU-part pile-up + 경계비용 | 최악 |
| ③ 오프라인 정적배분 | 미리 확정 | 동적 도착엔 pile-up 재발 | 부분채택(측정만) |
| **④ 통짜 라우팅** | task 통째 배정 + 비율/균형 그리디 | 배분 알고리즘 필요 | **채택** |
