# 다중 task 배분 실측 결과 (16 워크로드)

> 환경: RTX 3060 Laptop GPU(6GB, OpenCL) + i5-11400H(6코어) / TFLite fp32 / cpu-cores=6
> 도구: `multitask_test/online.exe` (배분 + 실제 동시 실행 + 예측/실측 비교)
> 비용표: `profile.csv` (오프라인 측정). makespan = 벽시계 실측(ms).
> baseline: **ALL-GPU**=전부 GPU 직렬, **ALL-CPU**=전부 CPU 스레드, **SCHEDULED**=모델 최적 배분.

## 핵심 발견

### 1. 스케줄링 이득은 0.56x ~ 1.09x — 최고가 노이즈 수준, 최악은 심각한 손해
- **최고 이득 1.09x(each3)**. 뒤에서 보듯 측정 노이즈(±5~7%)와 겹쳐 사실상 무의미.
- **큰 손해 다수**: mob10 0.56x, mob100 0.64x, mob50 0.66x, yolo30 0.76x, mix100 0.91x.
- 즉 **스케줄링이 도움이 안 될 뿐 아니라 자주 해가 된다.**

### 2. 측정 노이즈 바닥 ≈ ±5~7% (중요)
- yolo8/lane6/wide4/bise5/bise20은 **CPU=0** → SCHEDULED 배분이 ALL-GPU와 **동일**한데도 makespan이 다름
  (예: lane6 20.23 vs 21.57 = 7% 차이). 같은 실행인데 이만큼 흔들림.
- → **1.0x ±7% 안의 "이득/손해"는 노이즈**. 실제 신호는 0.56~0.76x의 큰 손해뿐.

### 3. 손해의 원인 = "가벼운 모델을 CPU로 과잉 오프로딩"
- 스케줄러는 항상 **가장 싼 C를 가진 mobilenet/yolov4를 CPU로** 뺀다(배분 열 참조).
- 그런데 mobilenet은 GPU에서 극히 쌈(100개 all-gpu=111ms). CPU로 빼면(각 9.5ms, 6코어 경합)
  오히려 느려짐 → mob100: 111ms → 176ms(**0.64x**).
- 왜 잘못 뺐나: 비용표의 G(mobilenet 3.74ms)가 **실제 연속실행 GPU(~1ms)보다 부풀려져**,
  모델이 "GPU가 붐빈다"고 착각하고 CPU로 과잉 오프로딩.

### 4. 정적 비용표가 심하게 miscalibrated (gap −35% ~ +204%)
- yolov4/lanenet 다수는 예측이 **2~3배 과대**(+108~204%): 프로파일 G가 부풀려짐.
- 가벼운 것 오프로딩 시엔 예측이 **과소**(−35%): CPU 경합을 모델이 안 잡음.
- **양방향으로 다 틀림 → 잘못된 배분 결정을 유발.**

### 5. 무거운 단일 모델 버스트는 ~1.0x (배칭이 답)
- bise20(1.01x), wide4(1.00x): 전부 GPU에 남음(오프로딩 불가). 스케줄링=ALL-GPU.
- 여기선 **같은 모델 배칭**(BiseNet×20을 몇 번의 batch invoke로)이 유일한 레버.

---

## 결론

**이 환경(discrete GPU + fp32)에서 whole-task CPU/GPU 스케줄링은 실패한다.**
- 이득은 노이즈 수준(≤1.09x), 손해는 최대 0.56x.
- 원인: (a) GPU가 CPU보다 4~100배 빨라 CPU 오프로딩 여지가 적고,
  (b) 정적 비용표가 심하게 어긋나(−35~+204%) 잘못된 배분을 강행.
- **안전한 정책은 그냥 ALL-GPU.** 스케줄러가 그걸 못 이긴다.

## 다음 레버 (실측이 가리키는 방향)
1. **배칭** — 같은 모델 버스트(bise20, mob100)에서 GPU를 batch로 묶기.
2. **CPU 경쟁력** — int8 양자화로 C를 낮춰야 CPU 오프로딩이 의미. (LaLaRAND)
3. **온라인 재측정 + 보수적 마진** — 정적 비용표 대신 실행 중 실측으로 갱신하고,
   "확실히 이득일 때만" 오프로딩(아니면 ALL-GPU 유지)해 손해 방지.
